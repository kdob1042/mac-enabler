# コンパクション・引き継ぎプロトコル

## 目的

会話のコンテキストが圧縮されても、作業を最初からやり直さず、GitHub上の状態から再開できるようにする。

## できることとできないこと

- ChatGPT／Codexのコンパクションや自動要約はホスト側の機能であり、リポジトリから強制できない。
- `mac-enabler` が保証するのは、コンパクション前に再開に必要な状態を保存する手順である。
- モデルの切り替えも、現在のUIが自動ルーティングを提供しない場合は強制できない。ルーターは必要能力と選択プロファイルを決める。

## 基本のモデル導線

1. まず `luna_max` で既存ソースとの関係、変更箇所、影響範囲を解析する。
2. 実装へ移る前に、作業状態を保存して必要ならコンパクションする。
3. コンパクション後に実装難易度を再判定し、難しい設計・実装なら `astra_light`、簡単なら `luna_max` を使う。
4. 破壊的変更、本番、移行、認証情報、公開契約に関わる場合は、難易度にかかわらず `astra_light` を使う。

ルーターを使う場合の例：

```bash
node scripts/route-task.mjs --phase source_analysis --task "既存ソースとの関係と変更箇所を特定する"
node scripts/route-task.mjs --phase implementation --task "難しい実装を行う"
node scripts/route-task.mjs --phase implementation --task "小さな文言修正を実装する"
```

## セッションを切り替える目安

コンパクションだけでなく、次の場合もIssue／PRへ現在地を保存して新しいセッションへ切り替える。

- 1つのIssueで実装・ツール履歴が大きくなり、次の独立した作業単位へ進むとき
- レビューと修正の往復が増え、過去の巨大なコンテキストを毎回持ち回る状態になったとき
- 別Issueへ移るとき

ただし、小さな修正ごとに機械的に新規セッションへ分割しない。再利用すべき文脈がまとまっている間は同じセッションを使い、独立単位へ移る境界で切る。

## レビュー・検証の燃費ルール

- reviewerは可能な限り1回で指摘をまとめ、関連修正をまとめて反映し、最後に再確認する。
- 同じ変更に対して細かな `review → fix → review` を繰り返さない。
- 長時間のtest／build／deployを別agentへ監視させない。
- 実行中コマンドを短い間隔で何度もpollせず、可能なら完了まで待ってexit codeと最終ログを確認する。
- まず変更範囲に近い検証を行い、全体test／buildは完了境界でまとめて行う。

## コンパクション前

次の情報を、Issueコメント・PR本文／コメントなど対象リポジトリで定めた永続的な場所へ保存する。

```markdown
## Handoff packet

- Goal:
- Scope and constraints:
- Route:
- Model profile:
- Source of truth:
- Branch / PR:
- Changed files:
- Tests and results:
- Remaining work:
- Unresolved decisions:
- Next action:
```

短い作業でも、少なくとも「現在地」と「次の一手」は残す。失敗した検証を成功扱いにしない。

## コンパクション後

1. 対象リポジトリのルートと適用範囲内の `AGENTS.md` を読む。
2. 最新のIssue／PRと引き継ぎパケットを読む。
3. ブランチ、PR、変更ファイル、未コミット状態を確認する。
4. パケットの `Next action` から再開する。
5. 既に行った探索を理由なく繰り返さない。

## 保存先の優先順位

1. 対象リポジトリのIssue／PR
2. 対象リポジトリが定める作業状態ファイル
3. 最後の手段として会話内の引き継ぎ文

会話だけを正本にしない。
